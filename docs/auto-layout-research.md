# Auto-layout: irregular nesting and Gridfinity footprint research

Research date: 2026-10-03. Research only; no production implementation. **Measured follow-up:** [the 1,609-evaluation benchmark](auto-layout-benchmark.md) recommends 1 mm raster/bitset placement as the primary candidate for new sizing modes, with coarse-to-fine angles as the smallest current-placer improvement. Use that report for measured tradeoffs; the initial hypotheses and ranking below are not the current implementation recommendation.

## Problem and current limitations

This is rigid, non-mirrored **irregular-polygon nesting**, not rectangular bin packing. Bounding boxes are useful lower-cost filters, but replacing traced outlines with boxes loses interlocking concavities. The current route constructs a polygon from a tool's point list without interior hole rings; a library's hole support is therefore not an immediate feature of this input contract.

[`auto_layout.py`](../backend/app/services/auto_layout.py) screens 72 absolute orientations at 5° on obstacle-bounding-box/bin-wall contacts; only the best four orientations receive the 2 mm position-grid search. It places tools sequentially without revisiting earlier choices. Each placement minimizes `(outside polygon area, aggregate bbox area, y, x)`. Obstacles are buffered by the requested tool clearance; strict `intersects` rejects exact contact. [`routes.py`](../backend/app/api/routes.py), `auto_layout_bin`, sorts by **unrotated height**, passes the usable rectangular interior, and reports tools that do not fit. These are separate restrictions: insertion order, placement candidates, angle screening, and local rather than whole-layout scoring.

Preserve [the coordinate contract](gotchas.md#bin-placements-and-auto-arrange): Y-down layout coordinates, absolute rotations, and reported `x/y` as the placed outline's **minimum corner**, not an engine's reference-point translation. Preserve every requested tool in a reported result; an overflow layout is diagnostic, not a feasible optimum. The synchronous endpoint has a practical request/proxy deadline even though its threadpool leaves the event loop responsive.

### Three different objectives

The following are distinct optimization problems, not interchangeable score tweaks:

| User mode | Primary feasible objective | Practical approach |
|---|---|---|
| **Fix X or Y; compute the other side** | All tools fit with physical clearances; minimize the free **Gridfinity dimension** | Irregular strip packing. Keep the specified side fixed, optimize the other side, then evaluate supported discrete dimensions using the actual interior geometry. Swap axes for fixed Y. |
| **Both X and Y are limits** | All tools fit inside both limits; then minimize the occupied/enclosing rectangle | Constrained two-dimensional compaction. Rank complete feasible layouts ahead of every overflow layout; compare occupied rectangle area, then deterministic tie-breaks. If the output bin is resized, compare the resulting discrete Gridfinity rectangle as well. |
| **Nonrectangular connected footprint** | All tools fit; minimize the number of enabled **edge-connected Gridfinity cells** | Joint layout-and-cell-mask optimization. Count required connector cells; diagonal-only contact is not connectivity. Validate the actual printable footprint, not raw outline pixel coverage. |

For the first mode, the schema already accepts half-grid dimensions; the free side should search those supported values, not claim an arbitrary millimetre optimum. A feasible larger strip is a useful seed for smaller candidates. **Do not binary-search on heuristic success/failure as though failure proved infeasibility:** the existence of a layout is monotone under enlarging a rectangular interior, but a greedy solver's success need not be. Enumerating supported smaller dimensions under a shared budget is safer; retain the smallest verified feasible result. Umetani et al.'s strip algorithm instead repeatedly shrinks/extends a strip and repairs overlap [1]; this is evidence for the approach class, not a Gridfinity implementation.

For the second mode, a smaller bbox with one protruding tool must not defeat a larger rectangle that contains all tools. If full fit is not found, keep an explicitly labelled fallback: maximize fully fitted tool count, then minimize total outside area, then compactness. Do not silently drop difficult tools. For current editor behavior, [auto-size happens after an auto-arrange targeting the requested bin](usage/bin-layout.md#auto-arrange); an expanded display does not retrospectively prove that the requested interior fit.

**“Smallest possible” needs qualification.** These heuristics return the best validated result found within a budget. A global minimum requires an exact model and a matching lower-bound/infeasibility certificate. Exhausting permutations, a position grid, or selected angles proves at most optimality within those restrictions, not over continuous rigid placements.

## Placement engines versus search strategies

A **placement engine** answers where a selected oriented tool can go: current Shapely collision/grid search, no-fit polygons (NFPs), scanline/raster collision checks, or a separation/compaction engine. A **search strategy** decides which layouts to explore: multiple orders, local moves, annealing, genetic/memetic search, or beam search. They compose: NFP + order local search, raster + beam, or annealing + remove/reinsert. A genetic algorithm does not itself solve concave geometry; a perfect NFP does not choose a globally good order. The original SVGnest design explicitly makes this distinction [4], and López-Camacho et al.'s selection-heuristic study pairs selection with placement [3].

## Alternatives and original pre-benchmark ranking

This initial ordering weighed anticipated user value, implementation cost, request latency, and six-month maintenance. It was **not** measured on real Tracefinity projects. The [subsequent benchmark](auto-layout-benchmark.md) supersedes its adoption priorities; the algorithm descriptions and theoretical limitations remain relevant.

### 1. Bounded deterministic multi-start/order search; then insertion/remove-reinsert

**First choice for rectangular modes.** Keep the current geometry engine. Seed with the current height order, decreasing polygon area, long-axis/bbox size, and a small reproducible set of alternative orders. Score **whole returned layouts** against the selected mode, preserving the baseline as incumbent. Try cheap permutation moves (swap, moving one tool earlier); only after that add remove/reinsert of an overflowing or badly blocking tool, optionally rebuilding the affected suffix. Rebuilding a complete candidate is initially simpler than maintaining mutable obstacle caches correctly.

This directly attacks irreversible greedy commitments. Order and placement changes are actual neighborhood operators in Sato et al.'s original simulated-annealing nesting algorithm [2]; SVGnest evolves order and orientation [4]. The DJD paper shows selection can matter, but its reported experiments are on **convex** polygons, so it does not establish gains for traced concave tools [3].

Cost is approximately multiple existing solves unless rotations/preprocessing can be reused within a request. Start with a modest fixed number of candidates and a shared deadline; exhaustive permutations do not scale. Parent smoke results below support testing this first, but show that compactness gains do not necessarily increase fit count.

### 2. Concavity-aware placement: NFP/Minkowski sums and inner-fit regions

**Most principled placement-engine improvement.** For fixed orientations and consistently normalized reference points, the configuration-space obstacle is `A ⊕ (-B)`; subtract translated pair obstacles from the item's inner-fit region to obtain feasible translations [1, 2]. This exposes placements inside elbows/overhangs that bbox contacts miss, without blindly scanning every grid point. For a rectangular bin and min-corner coordinates, the inner-fit region is simply `[0, W-w] × [0, H-h]`; do not implement a general inner-fit polygon unless nonrectangular bins require it.

Concave NFPs can be constructed using convex decomposition plus unions of pairwise Minkowski sums, or orbital methods [1, 2, 4]. They can have multiple loops, holes, narrow channels, and degenerate perfect-fit locations. Returning only an outer hull is not equivalent. Robustness and dense outlines are genuine engineering costs; Rocha's original NFP work specifically addresses high vertex counts, numerical errors, holes, and perfect fits [7]. Its continuous-angle discussion also explains why indiscriminate pair/angle precomputation is unattractive.

Use **lazy per-request** pair/orientation caching, not every pair of 72×72 angles upfront. At worst the number of orientation-pair entries grows like `n²r²`, before polygon complexity. Repeated order trials can amortize entries; continuously changing orientations largely defeats reuse.

Clearance must be represented consistently: an obstacle inflated by `c` against an uninflated moving polygon, or both inflated by `c/2`, not both by `c`. Boundary/wall clearance is a separate physical constraint. Approximate circular offsets and numerical contact tolerances still require final validation on original outlines. Current strict-contact behavior should not accidentally change during an engine replacement.

**Smaller experiment before a full NFP implementation:** add a bounded set of polygon vertex/edge contact proposals, then exact Shapely checks. This is only an incomplete candidate heuristic, not a robust NFP; it can miss edge-interior and multi-obstacle contacts. Do not advertise full concavity support from it. Rank 2 because of its targeted geometry value, but adopt only if rank 1 leaves characteristic interlocking failures or grid-search cost dominates.

### 3. Small beam/lookahead search; cheap collision-safe compaction

A beam retains a few distinct partial layouts instead of irrevocably keeping one. Branch over a small set of next tools, orientations, and placements; complete promising states with the existing greedy solver and compare complete results. Near-identical states should not consume the whole beam. Merely branching over the same bbox contacts cannot recover concavity placements that the engine never proposes.

This has a credible source implementation: PackingSolver's **irregular** tree search uses trapezoidal geometry and iterative beam search with a timer and bounded queues [5]. That does not prove a Python beam around this packer will be fast. Each beam state brings geometry/state copies and repeated collision work. Prefer order multi-start first; try a very narrow beam only for cases where one-step alternatives remain inadequate.

Separately, a feasible layout can be compacted by collision-safe coordinate moves/reinsertions. Axis sliding alone can jam in local minima; naive endpoint-only collision checks are not a general continuous-motion algorithm. More powerful overlap-minimization approaches deliberately enter infeasible layouts and then repair them: Umetani et al. alternate horizontal/vertical translation searches using directional penetration penalties and guided local search [1]. Never publish an unfinished repair state; preserve a separate feasible incumbent.

### 4. Raster/scanline/bitset engine when dense outlines are the bottleneck

Raster occupancy preserves concavity and holes at the selected resolution. Shifted bitsets offer simple repeated overlap checks; scanline runs avoid storing every filled pixel. Umetani and Murakami's original method uses **double scanline representations**, alternating coordinate line searches, and corner detection [6]—not a claim that a naive NumPy bitmap implementation has the same performance.

This is relevant because NumPy/OpenCV are already available and tool traces can be dense. However, it trades vertex dependence for pixel/rotation dependence: fine resolution, many orientations, and pairwise raster NFP caches can consume substantial memory. Pixel occupancy and discretized offsets can miss subpixel overlap or lose narrow valid gaps.

Use conservatively rasterized clearance shapes for proposals, followed by original-outline exact geometry validation. Record resolution and false rejection rates. Raster masks are also useful for the connected-cell objective, but **fine collision pixels are not the same thing as 42 mm footprint cells**. Choose this path only after profiling demonstrates dense-outline collision cost, rather than order or candidate quality, is limiting.

### 5. Simulated annealing, genetic, or memetic global search

Annealing can accept worse intermediate order/pose moves to escape local minima. SVGnest's GA encodes insertion order and discrete orientations, using NFPs for placement [4]. A memetic approach adds local improvement to evolutionary search; the original Zhou et al. paper reports this combination for irregular shapes, but only its publisher abstract was accessible here [8].

These are useful *after* cheap placement and local moves exist. Otherwise they multiply expensive greedy decodes without repairing their geometry blind spots. Annealing has temperature/schedule tuning; GA adds population/crossover/diversity management; memetic search adds another nested budget. No retrieved evidence establishes that those costs beat small multi-start on a synchronous request with a handful of traced tools. Do not introduce a population framework or background-job architecture just to try a few orders. A longer-running explicit optimization mode would be a different runtime decision.

### Why coarse-to-fine angles are not the leading recommendation

Coarse-to-fine can reduce angle cost, but current **bbox-contact screening can misrank the angle whose best placement is inside a concavity**. Refining only the winning angular neighborhoods can permanently exclude it. The same risk applies to narrowing the existing top-four grid refinement. Neither finer nor smarter angles undo an earlier bad insertion.

Keep angular refinement as a controlled ablation or a later tight-fit refinement, not the default explanation for failed nesting. Geometry-derived angles are another candidate source: PackingSolver selects edge/convex-hull axis alignments and bin-fit critical angles from permitted rotation ranges [5]. This is a heuristic set, not proof of optimal continuous rotation. Preserve diverse orientations and baseline candidates when testing it.

## Nonrectangular connected cells: additional problem, not a free raster feature

**Verified repository support:** [partial-bin generation](stl-generation.md#partial-bins) already accepts a row-major enabled-cell mask over `ceil(grid_x) × ceil(grid_y)`. Cut mode removes disabled 42×42 mm cells; shared-edge enabled cells can remain one component, while disconnected islands are exported separately. Connect-base mode keeps bases/bridges across disabled cells and spans the **full rectangular footprint**, so it does not meet a minimum-cell-footprint objective.

The current `_interior_clip_rect` in [`stl_generator_manifold.py`](../backend/app/services/stl_generator_manifold.py) is always the rectangle `grid*42 - 0.5`, inset by `max(wall_thickness, lip inset)`. It is **not mask-aware**. Generation builds the full shell/lip, then subtracts disabled-cell cutters; it does not reconstruct enclosing walls around all newly exposed polyomino boundaries. The schema permits masks without connectivity or hole validation. Existing rendering support therefore does **not** establish a closed, manufacturable arbitrary cell-mask bin with correctly seated pockets.

Parent's empty-bin geometry smoke observed: a 2×2 L-mask produced one manifold component, a diagonal pair two, and a 3×3 ring with its center removed one. The rectangular clip was identical for the L and diagonal masks. These observations prove those empty geometries were generated, **not** that tools fit, pockets are closed, or every ring/neck/lip configuration is supported.

**Recommended research path for this mode, before implementing production packing:**

1. Define/verify the printable interior for an enabled mask, including newly exposed walls, rounded/offset footprint, lip, pocket padding, and minimum viable connectors. Packing pair-clearance alone is insufficient. Check original tool/pocket geometry against that interior; touching cells in a raster is not manufacturing proof.
2. Given a layout, compute the cells needed to cover its **physical clearance envelopes**, with the actual grid origin and half-grid edge clipping. Optimize a translation relative to the grid as well as rotation/order: shifting a layout can change its cell count without changing its bbox. Define whether a clipped half-grid edge slot counts as one enabled cell or has an area-weighted cost; use enabled mask-entry count for the literal minimum-cell objective, and report occupied physical area separately.
3. Connect required components through additional shared-edge cells. For fixed required cells, minimizing selected unit-cost graph nodes is a node-weighted Steiner-type subproblem [9]; independent shortest connectors are a simple heuristic and can duplicate costs or miss a better shared connector. All required coverage cells must remain enabled, and connector cells count toward the objective.
4. Feed `(valid all-fit, enabled cell count, deterministic compactness tie-break)` back into order/pose search. Optimizing a mask only after a bbox-optimal layout is **not** joint optimization. Recompute coverage/connectors after moves; conservatively validate the final footprint and tool placement.
5. Default to a single **4-neighbor connected, hole-free** footprint until closed inner boundaries and topology are proven supported. Fill enclosed disabled regions if necessary and count the added cells. Tool holes, NFP holes, and holes in the *bin footprint* are three different concepts; support for one does not certify the others.

For a tiny exact experiment, enumerate finite validated tool poses, select one per tool, forbid intersecting/clearance-conflicting pose pairs, select every required cell, and enforce selected-cell connectivity with rooted flow/cuts. Minimize selected cells, including connectors. This is a proposed discrete mathematical model, not an existing drop-in implementation. It can prove an optimum only over its enumerated poses/cell domain, with manufacturability and no-hole restrictions included; it cannot certify the unrestricted continuous problem. None of the investigated nesting libraries jointly optimizes Tracefinity's cell mask and its physical boundary construction.

PackingSolver objectives include knapsack and open dimension X/Y. For a fixed single-bin comparison, explicitly use one bin and unit item profits if maximizing fit **count**: binding documentation says default profit is **area**. Require all requested items before comparing compactness. For free-side sizing, use open-dimension or discrete-bin feasibility evaluation with Tracefinity's interior sizes. Do not assume its default objective, or an XY mode with its own aspect-ratio setting, matches constrained minimum rectangle area. A fixed nonrectangular bin can be supplied for feasibility, but choosing a minimum connected cell mask remains Tracefinity-specific. Exact original-outline validation remains necessary after any engine's simplification/scaling.

## Do similar arrangers optimize appearance?

Usually, the exposed objective is fit/material use and compactness, not visual design. A result may look orderly because parts are tightly placed, but that is not the same as an objective for symmetry, grouping, aligned axes, consistent rotations, or balanced whitespace.

- **SVGnest** uses no-fit/inner-fit placement with a genetic search over item order and discrete rotations. Its placement worker scores a candidate by the enclosing bounds (`2 × width + height`) and breaks ties by position; its fitness penalizes extra sheets and unplaced parts. The source explicitly avoids convex-hull placement because it can create “oddly shaped nests,” but that bounding-box proxy is not a symmetry or regularity score. [Placement worker](https://github.com/Jack000/SVGnest/blob/master/util/placementworker.js), [fitness/search source](https://github.com/Jack000/SVGnest/blob/master/svgnest.js).
- **PrusaSlicer/libnest2d** uses NFP placement, first-fit selection and local optimization. Its default objective is packing efficiency, with an alignment option for the resulting pile (center or a corner). The library API also permits custom scoring that can shape the pile, but that is an extension seam—not evidence of a built-in aesthetic mode in PrusaSlicer's UI. The inspected libnest2d README limits its geometry support to convex closed polygons without holes/concavities. [libnest2d README](https://github.com/tamasmeszaros/libnest2d), [placer API/source](https://github.com/tamasmeszaros/libnest2d/blob/master/include/libnest2d/placers/nfpplacer.hpp), [PrusaSlicer arrange documentation](https://help.prusa3d.com/article/auto-arrange-tool_1770).

For Tracefinity, the shared result score currently prioritizes the number of tools inside the requested bin and then minimizes the occupied bounding-box area (`auto_layout_geometry.py`, `LayoutGeometry.score`). Neither stage asks for alignment, symmetry, grouping, or visual balance. A visually cleaner mode would therefore be a distinct secondary preference, applied only after preserving fit and the requested bin-size/compactness objective; otherwise it can trade away usable space or fitting tools. Evidence here covers these named projects and sources, not every commercial nesting product.

## Illustrative measured smoke, not a benchmark

The parent ran the current packer in-memory on three synthetic polygons, 2 mm clearance and the default position step: `bar=box(-30,-10,30,10)`, `long=box(-15,-40,15,40)`, `elbow=Polygon([(0,0),(40,0),(40,10),(20,10),(20,25),(0,25)])`. The height-descending baseline order was `(long, elbow, bar)`.

| Interior | Search | Fully fitted | Total outside area (mm²) | Aggregate bbox (mm²) | Observed elapsed |
|---|---|---:|---:|---:|---:|
| 100×80 mm | Baseline, 5° | 3 | 0 | 6320 | 0.573 s |
| 100×80 mm | Same order, 1° | 3 | 0 | 6320 | 1.456 s |
| 100×80 mm | Best of six orders, 5° | 3 | 0 | 4836 | 2.749 s for all six |
| 80×60 mm | Baseline, 5° | 2 | 416 | 5544 | 0.808 s |
| 80×60 mm | Same order, 1° | 2 | 405.717 | 6286.478 | 2.069 s |
| 80×60 mm | Best outside area among six orders, 5° | 2 | 250 | 5814 | 4.238 s for all six |

At 100×80, the best order `(bar, long, elbow)` reduced bbox area **23.48%**; the fixed bin's footprint was unchanged. Parent asserted all three returned placements, ≥2 mm pairwise distance within numerical tolerance, and min-corner reporting. At 80×60, neither approach increased fit count; finer angles slightly reduced outside area but enlarged the bbox. These are single-run, noisy measurements on rectangles plus an elbow, not dense traces, statistical latency estimates, or evidence of universally better fit. This research worker did not rerun them or run tests/build/lint.

## Apples-to-apples benchmark plan

1. **Freeze inputs and constraints.** Same original outlines/IDs, clearances, interior geometry, no mirroring, coordinate conventions, and requested mode. Include real dense traces plus small controlled sets: long tools, interlocking elbows, near-boundary fits, impossible oversized tools, narrow necks, holes only where represented by the product, and order-sensitive sets. Keep unsimplified outlines for validation; report any proposal simplification tolerance.
2. **Separate objective tracks.** Fixed X/Y: smallest validated supported free dimension. Both limits: full fit first, then occupied rectangle/discrete resized-bin area. Connected cells: full fit first, then enabled count including connectors/hole fills, with physical mask validation. Also record the existing fixed-bin behavior and unconstrained autosize separately; never compare fixed-bin overflow reduction against a larger autosized bin as though it were the same win.
3. **Ablate one change at a time.** Current baseline; same engine + order trials; + remove/reinsert; concavity candidates/NFP; narrow beam; raster proposals; external irregular solver; angle-only refinement. Use equal total wall-clock budgets, not equal iteration counts. Include preprocessing, conversions and final validation; distinguish cold/warm cost and memory. For NFP caching, report entries and build time.
4. **Measure validity and outcome.** Returned/missing tool count, fully fitted count, unfitted IDs, total/max outside area, requested clearance violations, occupied bbox, discrete output dimensions/cell count, shared-edge connected components, footprint holes and generated-body/pocket validity. Keep overflow diagnostics separate from feasible solutions. An empty-bin manifold is not a pocket-fitting test.
5. **Measure latency/determinism.** End-to-end p50/p95/worst time under the intended request deadline and concurrent workload; repeat stochastic methods with fixed recorded seeds and repeat deterministic ties. Record time-to-first feasible and best result versus elapsed time. A fixed work budget can be reproducible; a wall-clock cutoff alone can stop at different iterations. Check cancellation/timeout does not return a partially repaired or incomplete result.
6. **Preserve the best.** Seed with the baseline, keep an independently validated incumbent, and never replace it with a worse result under that mode's score. Publish both quality and deadline misses. Time-limit failure means “no fitting layout found,” not “no fitting layout exists.”

**Decision gate:** implement the smallest successful change only after these comparisons. The measured order sensitivity merits a bounded multi-start experiment; NFP/raster/solver adoption needs actual traced-outline and request-latency evidence. Connected-cell output additionally needs a validated physical footprint contract. No universal runtime, optimality, or library speedup is established here.
